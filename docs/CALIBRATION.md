# 算法标定报告

> 阈值是怎么定出来的，以及为什么不能靠手调。
> 工具：`tools/calibrate.py`（可在本机跑，也可同步到 Linux 用多核加速）

---

## 一、为什么需要标定

原始阈值（`enter=18°`、`minMotion=0.6` 等）是**手调猜出来的**，只对着"干净正弦 + 白噪声"的合成数据做过自检，68 项全绿。

问题是这种波形和真人差得很远。真人深蹲包含：

| 因素 | 干净合成 | 真人 |
|---|---|---|
| 深度曲线 | 对称正弦 | 下蹲占 45%、起立占 55%，不对称 |
| 姿态漂移 | 无 | 手臂摆动、躯干前倾、鞋底摩擦，秒级低频变化 |
| 落地冲击 | 无 | 足底触地瞬间的衰减脉冲 |
| 生理微抖 | 白噪声 | 多频正弦（0.8/3.1/7.3 Hz）叠加 |
| 幅度差异 | 固定 | 半蹲到蹲底差 3 倍，因人而异 |
| 频率分布 | 固定 2 秒 | 康复慢蹲 4 秒 → 爆发蹲 0.8 秒 |

所以"在仿真上全绿"不等于"在真人身上能用"。这个报告就是把这些差异量化，然后对阈值做系统搜索。

## 二、8 个测试场景

| 场景 | 倾角幅度 | 位移幅度 | 周期 | 特点 |
|---|---|---|---|---|
| 标准蹲 | 45° | 0.45 m | 2.0 s | 基准情况 |
| 浅蹲 | 28° | 0.25 m | 1.8 s | 幅度小，容易漏 |
| 深蹲到底 | 62° | 0.60 m | 2.6 s | 幅度大 |
| 慢速康复蹲 | 35° | 0.30 m | 4.0 s | 慢到容易触发超时作废 |
| 快速爆发蹲 | 50° | 0.50 m | 1.0 s | 快到容易漏 |
| 晃手臂 | 48° | 0.45 m | 2.2 s | 手臂摆动大 |
| 躯干前倾 | 42° | 0.40 m | 2.0 s | 上身前倾污染倾角信号 |
| 高抬腿式 | 55° | 0.55 m | 1.6 s | 非标准深蹲 |

另有一组**干扰信号**（走路时的周期性起伏、日常活动），用于评估误计。

**评价指标用的是"最差场景准确率"而不是平均值** —— 因为一个用户蹲不准就流失了，平均值会把这个场景稀释掉。

## 三、标定过程中发现的三个 bug（都是真 bug，不是模型问题）

### ① 零点漂移补偿会「把深蹲幅度吸收掉」

`utils/squat-detector.js` 里有一段基准漂移补偿：

```js
if (sig < cfg.exit && this.linear < 0.4) {
  this.baseline = unit(lerpVec(this.baseline, g, alphaFor(dt, 15)))
}
```

原本只检查两个条件：相对基准的倾角小、线加速度小。

**问题**：下蹲刚开始时倾角还很小（< exit=12°），于是基准开始跟着重力走。等倾角涨到 34° 时，基准已经偏了 34°。回落时相对基准瞬间变 0 → 立刻触发退出 → **同一个深蹲被数两次**。

**修法**：加第三个条件 —— 相对**世界竖直方向**的绝对倾角也要小。

```js
this.absoluteTilt = Math.acos(clamp(g.z, -1, 1)) * RAD_TO_DEG   // 加速度计的 +z 就是重力反方向

if (sig < cfg.exit && this.linear < 0.4 && this.absoluteTilt < cfg.exit) { ... }
```

语义变成：**只有人真的站直了（绝对倾角也小），才允许基准跟着重力慢慢走。**

这一条已同步到 `band/src/common/squat-detector.js`。

### ② 信号生成器把波形画错了（耗时最长的一个坑）

原来的深度曲线：

```python
idx = np.where(k < split, k / split, (k - split) / (1 - split))
wave = 0.5 * (1 - np.cos(np.pi * idx))
```

在 `k = split` 处 `idx` 从 1 跳回 0，`wave` 也从 1 跳回 0 —— 等于「下蹲 → **瞬间站直** → 再下蹲」，一个周期里含**两次**完整深蹲。

状态机忠实地数了两次，所以出现「3 蹲数出 5 个」「25 蹲数出 49 个」= 196%。

**我一度以为是状态机重复触发**，改了状态机两轮都没修好。后来逐帧打印倾角轨迹，看到 `tilt` 从 33.47 在一帧内掉到 11.98，才定位到是波形本身不连续。

正确写法是一个连续的 0→1→0 三角：

```python
depth = np.where(k < split, k / split, 1.0 - (k - split) / (1.0 - split))
wave  = 0.5 * (1 - np.cos(np.pi * depth))
```

**教训**：仿真结果异常时，先打印波形验证信号本身合法，再怀疑算法。`make_signal` 现在内置断言：峰值必须接近设定深度、谷值必须 < 8°，否则直接报错。

### ③ 漂移幅度写反了

```python
drift = drift_wave * (sc.drift_amp / max(0.01, sc.drift_amp)) * sc.drift_amp
```

`sc.drift_amp / max(0.01, sc.drift_amp)` 恒等于 1，所以漂移幅度 = `drift_amp` 本身。而深度曲线 `curve` 范围是 0~1，**等于漂移和深蹲一样大**，谷值被顶到 19°，状态机卡在 bottom 出不来 → 漏检 50%。

修法：用明确的 `drift_ratio = 0.08` 限定漂移最多是深蹲幅度的 8%。

## 四、怎么用

### 本机跑（Windows / macOS）

```bash
node tools/simulate.js          # 算法仿真（快速反馈）
node tools/test-calibration.js  # 校准行为专项
python tools/calibrate.py --quick   # 阈值标定（需要 numpy）
```

### Linux 多核跑（推荐，标定较慢）

`lab` 机器（8 核）实测可用：

```bash
scp tools/calibrate.py lab:~/squad-calibrate.py
ssh lab
setsid nohup python3 -u squad-calibrate.py --quick --out best.json > calib.log 2>&1 < /dev/null &
tail -f calib.log
```

> **两个必须的注意点**（都踩过）：
> 1. 用 `setsid ... < /dev/null &` 彻底脱离 SSH 会话。否则 SSH 超时后
>    wrapper 进程会变成僵尸，**每次超时都会留下一套进程池抢核**。
>    我踩过：21 个 python 进程抢 8 核，load 19，标定卡死。清理：
>    `pkill -f squad-calibrate`
> 2. 用 `python3 -u` 关掉输出缓冲，否则日志要等进程结束才可见，
>    没法判断进度。

脚本用 `multiprocessing.Pool`（8 核），评估用**固定随机种子**，保证所有候选参数面对完全相同的测试集 —— 否则结果不可比。

搜索分两阶段：粗筛（粗步长快速淘汰）→ 在前 3 名附近细化。细化网格要控制规模：3 候选 × 4 × 4 × 4 × 3 ≈ 480 组。第一版取前 8 名、步长又密，组合出 9945 组，跑了一小时没出结果。

### 把结果写回代码

`best.json` 里的值对应 `utils/squat-detector.js` 的 `TILT_PRESET` / `LIFT_PRESET`，以及文件顶部的 `CALIB_STILL`。注意三处要同步：

- `utils/squat-detector.js`（小程序 + 网页版构建源）
- `band/src/common/squat-detector.js`（手环版，直接复制）
- `tools/calibrate.py` 里的 `TILT_PRESET_BASE` / `LIFT_PRESET_BASE`（Python 等价实现）

> ⚠️ 改 `squat-detector.js` 后必须跑 `node tools/build-web.js` 重新生成网页版。

### ⚠️ 标定完必须跑回归

**这是本项目最容易翻车的地方。** 第一轮标定给出 lift `enter=0.025`，看起来完美（8 场景 100%、误计 0），但写回 `squat-detector.js` 后 `simulate.js` 直接报：

```
FAIL 干扰 手持微晃5cm ×0   lift /medium → 12 (期望 0)
```

原因是**两套测试的场景不重叠**：标定的干扰信号只有"走路起伏 2~6cm"，而 `simulate.js` 测的是"手持小幅晃动 5cm"，后者更大、节律更像深蹲，标定时完全没考虑。

修法是给 `calibrate.py` 加了 `make_sway()`，把 8~12cm 的周期性晃动显式纳入目标函数，权重还给得最高（`sway_fp * 1.5`）—— 因为它就是"站着晃两下数字就跳"，最伤体感。

**所以流程是：标定 → 写回 → 跑全部 simulate/test-calibration → 有回归就说明目标函数漏了场景 → 补场景后重新标定。** 不要看到标定数字漂亮就直接写进代码。

## 五、标定结果的局限（必读）

**标定能保证的**：在覆盖 8 类人群/动作风格的信号上，不出现系统性漏计或系统性多计；参数对抖动、漂移、冲击有一定鲁棒性。

**标定不能保证的**：

1. **仿真 ≠ 真人。** 我的波形模型终究是模型。最可信的验证还是真机实测。
2. **推荐流程**：先用网页版或手环实测几种摆法，把实际倾角峰值/位移幅度记录下来，替换掉 `SCENARIOS` 里的估计值再重跑标定。这样才是真正的「用你的数据定你的阈值」。
3. **上下午不对称**。穿厚裤子和不穿、鞋跟高低，手环松紧，都会改变信号。灵敏度三档就是为此保留的手动逃生口。

## 六、手环场景的特殊考虑

手腕姿态会被手臂摆动污染，所以手环版**默认走 `lift`（垂直位移）模式**——手环塞不进裤袋，位移信号反而更稳。

标定结果里 `lift` 的 `enter` 是绝对位移（米）不是角度，含义是"一次深蹲至少要产生这么多个米的垂直位移才算数"。这个设计天然免疫"只晃了一下"，代价是**幅度太小的深蹲会被漏掉**（比如只蹲一半）。
